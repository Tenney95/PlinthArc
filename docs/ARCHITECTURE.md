# PlinthArc v0.1 Rust 底层架构决议

2026 年 11 月 26 日定案，待实现。首个验证环境为 Linux x86-64、RTX 4090 24 GB。本文确定控制进程、存储、调度和引擎接入边界。模型与工作流的文件契约见[运行时规范](SPEC.md)，各设备的速度和质量证据见[性能方案](REUSE.md)。

## 1. 一个程序，两个进程职责

```text
Arc 同源页面 ── 本机 HTTP ──┐
CLI ── 直接调用或本机 HTTP ─┴─ Plinth（数据目录的唯一协调者）
                                ├─ 模型库、预检、任务调度和交付
                                ├─ SQLite 索引、权重文件、素材和产物
                                └─ 内置 Pillar ── 独立引擎进程 ── GPU
```

首版使用 **一个 Cargo package**。库目标承载共用逻辑，二进制目标发布一个 `plintharc` 命令，`serve` 是其子命令。固定版本的引擎作为独立可执行文件调用。Arc 与 Rust 同仓构建。首批 Pillar 编译进 Plinth，模型包只能声明数据和能力。出现需要独立发布的适配器后，再为它设计跨进程版本协议。Cargo 原生支持这种库与二进制组合，Rust 原生 ABI 没有跨版本稳定保证。[Cargo targets](https://doc.rust-lang.org/cargo/reference/cargo-targets.html) · [Rust ABI](https://doc.rust-lang.org/reference/items/external-blocks.html#abi)

| Rust 模块 | 负责的内容 |
|---|---|
| `contract` 与 `workflow` | Serde 模型清单、请求、运行回执、错误和工作流导入。将受支持的 ComfyUI 图一次性转换成原生请求。 |
| `runtime` | 解析配置与资产、预检、受理任务、选择设备、调度、取消和恢复。决定何时发布成功。 |
| `store` | 管理 SQLite 事务、摘要与文件位置、原地登记、引用保护以及封存产物。负责将索引记录映射为受控文件读取。 |
| `pillars` | 将已校验的执行计划翻译成固定引擎支持的调用，启动和回收进程，报告阶段、失败和候选产物。第二个实现出现时，按两者实际共用的操作抽取接口。 |
| CLI 与 `http` | Clap、Tokio、Axum 负责入口、上传、轮询和 Range 读取。两种入口调用同一组应用操作，参数校验和状态迁移都在库中。 |

### CLI 与服务共用同一个模型库

- 每个规范化的本机数据目录只允许一个 Plinth 协调者。打开固定锁文件并在整个所有权期间持有 `File::try_lock` 的句柄。锁文件保留在原处，进程退出由操作系统释放锁。状态目录和数据库放本机磁盘，外置盘上的权重可原地登记。[Rust 文件锁](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock)
- 单独执行 CLI 命令时，若取得锁，直接调用库完成登记或生成。一次性生成持锁直到引擎退出和交付结束。`serve` 运行期间持续持锁，CLI 通过其本机接口操作同一个协调者。服务把本次实例标识、地址及 CLI 管理凭据放在仅当前用户可读的位置。服务退出后使凭据失效。网页 API 接收资产 ID 与模型摘要，接收本地路径的登记、重连命令另验 CLI 凭据。
- 遇到另一条独立 CLI 正在工作则报告目录忙。若 `serve` 的地址过期或连接中断，先核验当前所有者。只有实际取得锁才能接管，接管后先做恢复。关闭浏览器不会停止服务任务。

## 2. 一次生成的执行边界

1. **解析请求。** CLI、HTTP、原生预设和可导入的 ComfyUI 工作流共用规范中的 `model_digest`、`profile_id`、`operation`、`inputs`、`params`。模型能力、Pillar 实现和经过认证的设备配置取交集，产出同一套表单字段与预检结果。
2. **受理并冻结。** 先以幂等键查询已受理请求。请求指纹由规范化后的调用意图计算，保留有意义的数组顺序及随机种子选择。同键同指纹返回原 `run_id`，不同指纹返回冲突。新请求预检通过后，在同一短事务内复查唯一键、兑现一次实际种子、写入请求快照、组件与输入引用以及队列记录。提交后才可派发。重试已有请求不需要模型此刻仍在线。
3. **按设备派发。** 首版每个协调者选定一张实际运行卡，在服务启动或独立 CLI 执行时确定。设备 API 展示当前选择，回执记录实际物理设备和后端。队列按受理顺序派发。相同系统用户的 Plinth 实例按物理 GPU 标识共用一把设备锁，覆盖多个数据目录。取得设备后复核外部文件身份、可用资源和输出空间，持久写入已开始状态，再启动引擎。其他用户和程序的显存占用仍可能变化。跨设备重新运行须显式选择配置。
4. **执行整条流水线。** 内部执行计划固定引擎构建、配置、组件摘要与解析位置、输入顺序、有效参数、种子、设备和本次暂存目录。Pillar 只接收这份计划，文本条件、latent、去噪和 VAE 均在一个引擎中完成。生成请求与状态接口传递控制信息及资产引用，素材上传和产物读取走独立的流式接口。运行阶段变化写入快照，逐步进度在内存合并，浏览器按 `run_id` 轮询。
5. **核验并交付。** Plinth 核实文件类型、可解码性、尺寸和摘要。视频另核实帧数、帧率、时长和音轨。完整产物经第 4 节的发布流程进入历史，图片产物也能以原资产 ID 成为 H3 首帧。

## 3. 第一个 Pillar 采用 sd-cli

首个真实实现使用固定构建的 **stable-diffusion.cpp `sd-cli`，一条任务一个子进程**。Rust 把已校验的组件位置作为独立参数传入，在本次运行的私有目录写文件。这样能直接读取分布在不同磁盘的现有权重，也能在首次实现时验证退出、取消、音画和产物交付。代价是连续生成会重新加载模型，这一成本列入第一轮测量。

- 首批使用各角色可单独传入的文件。经验证的单文件 GGUF 和 Safetensors 可直接使用内容摘要文件名。遇到分片索引与目录模型时，须验证索引的每个引用，再提供规范允许的只读目录视图。固定构建支持此布局后才开放相应配置。[模型加载器](https://github.com/leejet/stable-diffusion.cpp/blob/52491bd9f1fc15281791723bdff13baab7fd6819/src/model_loader.cpp#L198-L234)
- 对 Z-Image-Turbo 先走一次完整出图。对 H3 使用明确的 DiT、文本编码器、视频 VAE 和音频 VAE，首帧图生再绑定原图。该版本省略音频 VAE 也可能成功生成无声视频，所以含原生音轨的配置必须在预检和交付各验证一次。首测 864×480、56 帧、24 fps，随后用 107 帧验收四秒以上的短片。先写有声 AVI，再按实际编码转为通过目标浏览器播放验证的 MP4，保留音轨。转码和发布耗时计入端到端时间。[H3 官方用法](https://github.com/leejet/stable-diffusion.cpp/blob/52491bd9f1fc15281791723bdff13baab7fd6819/docs/models/minimax_h3.md)
- Tokio 并发排空输出管道并限制诊断日志大小。仅上报引擎确实提供的进度，输出路径由本次运行分配。取消时停止本次进程及其受管子进程，超时再强制结束，等待回收后才释放设备。Linux 首机从固定存活的监督线程直接启动引擎，在创建子进程时传入设备锁句柄，库目录锁留在宿主。直接子进程在执行引擎前设置父线程退出信号并复核父 PID。宿主在启动与记录 PID 之间被硬杀时，设备锁仍随存活句柄持有，关闭最后一个句柄才可重新派发。辅助编码进程也由 Plinth 直接监督。产生额外子进程的配置须另验整棵进程树回收。重启遇到身份不明的占用时保留阻塞诊断。Windows 接入时验证 Job Object 的最后句柄关闭行为。[Tokio 子进程](https://docs.rs/tokio/latest/tokio/process/) · [Linux 父线程退出信号](https://man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html) · [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)
- **常驻优化从图片开始。** 用相同权重、输入和精度把一次性 CLI 与私有回环 `sd-server` 交错对比。后者已有模型上下文、文本条件缓存和取消接口。必须按计划绑定确切组件，验证换模型、取消再生成、同名权重和零额外权重副本。H3 的原生 HTTP 接口会把整个编码容器作为 Base64 返回，还须比较主机峰值内存与最终交付耗时。只在重复运行的端到端收益超过测量波动且质量、内存及恢复验收通过后，才发布相应常驻配置。[原生 API](https://github.com/leejet/stable-diffusion.cpp/blob/52491bd9f1fc15281791723bdff13baab7fd6819/examples/server/api.md) · [条件缓存](https://github.com/leejet/stable-diffusion.cpp/blob/52491bd9f1fc15281791723bdff13baab7fd6819/docs/guides/caching.md)

常驻 worker 按设备、引擎构建、模型与组件摘要、影响加载的选项识别。切换不兼容配置时先卸载旧上下文。显存不足时报告失败阶段，可由用户重选已验证的卸载或量化配置。若将来需要常驻且文件交付受 HTTP 限制，可在隔离 worker 内接上游 C API。Mold、edge-dit、Metal 或 TensorRT 的候选也遵守相同执行边界。[sd.cpp C API](https://github.com/leejet/stable-diffusion.cpp/blob/52491bd9f1fc15281791723bdff13baab7fd6819/include/stable-diffusion.h) · [后端候选与实测条件](REUSE.md)

## 4. 文件、数据库与恢复

**SQLite 管理身份、引用、队列、运行状态和产物可见性。文件系统保存字节。** 原始清单、不可变的托管权重、登记在外部的权重、输入素材及每次运行的产物沿用规范中的位置。`runs/<run_id>/` 中的回执和清单用于审计及恢复，API 以 SQLite 中已提交的状态和索引为准。

首版用 `rusqlite` 的 bundled SQLite。一条连接由专用阻塞线程持有，Tokio 经有界队列提交短数据库操作。对单连接选择回滚日志 `DELETE`、`synchronous=EXTRA` 和 `foreign_keys=ON`。哈希、下载、媒体解码、产物文件同步、推理及进程等待均在数据库事务外。高频采样进度不会触发逐步同步写盘。若出现独立读连接且读写争用可测，再评估 WAL。[Rusqlite](https://github.com/rusqlite/rusqlite) · [SQLite 事务](https://sqlite.org/lang_transaction.html) · [同步级别](https://sqlite.org/pragma.html#pragma_synchronous)

**模型登记与清理。** 托管导入时在目标卷暂存，流式算 SHA-256、校验大小并同步。最终文件按摘要无覆盖发布，持久化所需的目录项，再以事务提交模型清单与全部组件引用。并发导入相同字节复用同一文件。协调者串行处理最后的发布、登记与清理决议，长时间下载和哈希在外进行。清理时重新检查模型、已受理任务及常驻 worker 的引用。无索引的孤件先对账，只删除明确无引用的托管内容。原地登记保留摘要和文件身份，发现变更须重新校验或重连。硬链接共享底层文件，不能冻结用户在外部盘上原位改写的内容。[统一模型库规范](SPEC.md#2-统一模型库) · [同盘发布的限制](https://docs.rs/tempfile/latest/tempfile/struct.NamedTempFile.html#method.persist_noclobber)

**任务提交与产物提交分开。** 引擎只写本次暂存目录。确认退出、数据可读和输出符合请求后，Plinth 写入完成清单，包含运行 ID、请求指纹、各产物的相对路径、实际规格和摘要。先同步文件和清单，再在同卷封存整个产物目录，同步必要的目录项。最后一个 SQLite 事务同时登记资产与成功状态。Linux 对文件和目录分别同步，其他平台按各自的持久化语义实机验收。[文件与目录同步](https://man7.org/linux/man-pages/man2/fsync.2.html)

正常状态依次为 `queued → running → delivery_pending → publishing → succeeded`。`delivery_pending` 表示推理已停、存在可验证的完整产物。发布暂时失败时回到这里，记录错误并允许只重试交付。取消先获得状态更新权则进入 `cancel_requested`，等资源收回后进入 `cancelled`。`failed`、`interrupted`、`cancelled` 和 `succeeded` 都是终态。只有已提交的资产 ID 可以通过 API 读取。移除模型登记时保留历史回执中的模型摘要，组件清理只处理无活引用的托管文件。

| 中断或竞争位置 | 唯一协调者的处理 |
|---|---|
| 已受理，尚在排队 | 队列记录保留。仅能证明从未派发的任务可按原顺序继续。已开始记录必须早于引擎启动。 |
| 已记开始，派发结果未知，或引擎中途退出 | 先核验旧进程身份并回收设备。有完整清单按交付规则对账。其余情况，已知引擎报错则记失败，宿主重启后无法判定则记 `interrupted` 并留下失败阶段。用户主动重跑会得到新的运行 ID。 |
| 取消与发布同时到达 | 排队任务可直接取消。运行中先持久化取消请求，等引擎停止才记 `cancelled`。发布前在数据库以条件更新争取发布权，已受理的取消阻止发布，已取得发布权的任务向取消方返回当前状态。 |
| 已有完整清单及文件，数据库尚未提交成功 | 对账时复核运行 ID、请求指纹、摘要、文件与取消状态。若已封存且已取得发布权，幂等补齐索引。只有完整暂存且未接受取消时转为 `delivery_pending`，可用同一个 `run_id` 重试交付。残缺产物保留明确的中断状态。两种恢复均不派发推理。 |
| 已提交成功，客户端未收到答复 | 凭幂等键取回原 `run_id`，或按运行 ID 读状态。成功快照与可读产物一起可见。 |

## 5. 实施顺序与退出条件

先用固定上游构建完成实施方案中里程碑 0 的独立冒烟验证，再按下列顺序集成到 Plinth。

| 步骤 | 可验收的结果 |
|---|---|
| 1 · 单机控制核心 | CLI 登记一套模型并预检。验证单所有者、同名异内容、异名同内容、并发登记与外部盘重连。 |
| 2 · 第一个引擎 | 在指定的 4090 上从 CLI 跑通 Z-Image-Turbo 和一条 H3 短片，保留实际配置、原生音轨、端到端时间及主机与设备峰值内存。同时从两个数据目录选同一张卡，验证只有一个引擎运行。分别在派发前、子进程刚创建及采样中硬杀宿主，核对设备释放、任务对账和下一次生成。 |
| 3 · 服务与耐久性 | 在 `serve` 运行时从 CLI 原地登记、从 Arc 提交。模拟回执丢失、两次相同提交、提交键冲突、封存后崩溃、磁盘写满和清理与运行竞争。核对运行数、资产数和实际引擎启动次数。 |
| 4 · 工作流与性能 | SDXL 原生图和基础 ComfyUI 导入生成等价请求。对照首次出图、改种子连出三张、换模型、H3 音画可播放时间与取消后再次生成。按设备和操作公布通过的配置。 |
